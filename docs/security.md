# Authentication, permissions and cheating

The existing server uses `online-mode=false` for the owner's TLauncher setup. In this mode the server does not establish Mojang/Microsoft account identity. Anyone able to connect may claim an allowed name. Whitelist membership is therefore not proof of identity, and an attacker claiming an operator's identity may gain powerful permissions. A small player count and an obscure tunnel name do not fix this.

Prefer authenticated Minecraft accounts and `online-mode=true`. The example enables this, whitelist enforcement, and disables RCON and query. Do not apply it blindly to the current world: UUIDs, inventories, whitelists and OP mappings can change. Back up private identity data, test both players in isolation, and plan migration before switching. No script toggles authentication or adds operators.

If offline mode must remain, consider [EasyAuth](https://modrinth.com/mod/easyauth), a Fabric authentication mod whose publisher lists 26.3 support as of 2026-10-11. It requires Fabric API. Its documented features include blocking unauthenticated actions, account login, and session/premium identity handling. This is a candidate, **not a validated security deployment**: confirm the exact Fabric 26.3 release, loader requirements, dependencies and [current configuration documentation](https://github.com/NikitaCartes/EasyAuth/wiki) before installing on an isolated copy.

Evaluate registration ownership before opening the tunnel: reserve both legitimate player identities so an attacker cannot register them first. Use unique passwords, disable or tightly evaluate IP-based remembered sessions behind a relay, and verify how the relay presents client IPs. Check timeout behavior, reconnects, duplicate names, blocked pre-login commands/movement/inventory, and UUID behavior. Do not enable premium auto-login merely because a username matches a premium name; test the documented account-verification flow. Protect authentication databases and backups as secrets. An in-game password layer is not equivalent to authenticated Minecraft sessions and should not be assumed to encrypt offline-mode network traffic.

Grant no OP for routine survival play. Prefer server-console administration and narrowly scoped, version-compatible permissions if needed. Authentication prevents some identity abuse; it does not prevent an authenticated player from using a cheat client. Server-side validation, observation and trusted membership still matter. No anti-cheat mod is endorsed without confirming compatibility and testing false positives, especially during network jitter.

Never commit world/player files, real whitelist/OP lists, logs, crash reports, auth databases, RCON passwords, playit tokens, hostnames or private network details. `.gitignore` is a default-deny aid, not a secret scanner: review staged content and history before every push. If a secret is published, revoke/rotate it immediately and then clean repository history as needed.
